# Focodex 終了経路・プロセス管理の整合性調査

調査日: 2026-10-31。対象は調査時点のコード。Surfaceのインストール済みHostとの一致やFirefox実機の切断タイミングは確認していない。コード読解と既存テストの確認に基づき、再現済みと可能性を区別する。調査後、終了確認の再試行を実装したため、以下の単発確認に関する記述は調査時点のものである。

## 構造と管理境界

- `extension/background.js:1-9` は画面を開く・既存タブに移動するだけ。`extension/probe.js:516-519` の各画面が `runtime.connectNative("focodex")` でHostへ直接接続する。接続後に `projects` を要求し（同:705-706）、明示的な再接続操作がある。`draft-background.js` のポートは別の入力バッファ用で、CodexのNative Messaging中継ではない。
- HostはNative MessagingのstdinとCodexのstdoutを監視する（`native_host/focodex.py:485-488,1335-1347`）。`run`・`models`は各回 `Popen(..., start_new_session=True)` で別セッション・プロセスグループを起動する（同:901-935）。先にtoken・boot ID等を実行記録へ原子的に保存する（同:200-211,923-929）。
- 同じ設定ファイルのHost間は同じ `config.lock` と `config.execution.json` で排他する（同:263-301,724-736）。別設定間や外部の手動Codex/Gitは対象外。プロセスグループは子孫ツリーそのものではなく、別グループ・別セッションに移った子孫は対象外。
- UIの要求にはUUIDを付け、結果は接続と要求IDで照合する（`extension/probe.js:318-327,516-542,624-651,738-755`）。Hostは起動ごとに結果・thread等を初期化し、設定単位のロックを終了処理まで保持する（`native_host/focodex.py:901-921,665-669`）。

## 終了経路

| 操作・条件 | 現行の経路と結果 |
| --- | --- |
| タブを閉じる・再読み込み | UIにはunload時の明示stop処理がない。Native接続切断でHostのstdinがEOFになる場合、`Host.loop` がreturnし `finally` から `cleanup()` を呼ぶ（`focodex.py:1343-1349,1385-1387`）。再読み込み後は新しい画面・接続。FirefoxからEOFが届くこと自体の実機確認は未実施。 |
| Firefox正常終了 | 同様にEOFまたはHostへのSIGTERMならcleanupへ進む。ブラウザ側の実際の終了順序と猶予は未検証。 |
| Firefox異常終了 | Hostが生存してEOFを処理できればcleanup。HostもSIGKILL等で終了、あるいは実行不能ならfinallyは保証されず、子が残りうる。実行記録は残る設計。 |
| リポジトリ・ワークスペース変更 | 通常UIではbusy中の選択を無効化（`probe.js:470-478`）。終了後の変更でGit画面をリセットし、モデル再取得を開始（同:61-71,318-327,400-407）。切替それ自体には停止要求はない。旧結果表示は残る（後述）。 |
| 実行中に停止ボタン | `stop` は対象IDを照合し、thread/turn IDが揃えば `turn/interrupt` を送信。未取得なら後で送信（`focodex.py:702-705,862-869,1289-1295`）。5秒で結果がなければcleanup（同:1338-1340）。 |
| 通常完了・RPCエラー・Codex stdout EOF・180秒超 | `finish()` からcleanup。モデル取得完了もcleanup後に一覧を公開（`focodex.py:673-700,1208-1214,1249-1265,1323-1342,1373-1376`）。承認・質問待ち中は180秒制限が停止する（同:1341）。 |
| HostのSIGTERM/SIGINT | signal handlerが `SystemExit` を発生させ、loopのfinallyでcleanup（`focodex.py:1385-1397`）。ただしその最中の再シグナルや例外、SIGKILLでは完遂を保証しない。 |
| Host強制終了・クラッシュ | Pythonのfinallyを実行できない場合は停止要求なし。OSロックは解放されるが永続実行記録は残り、同一設定からの競合操作を拒否する（`focodex.py:665-669,724-735`）。 |
| 終了確認失敗 | 記録と `cleanup_uncertain` を残し、同一Hostはrun/models/Gitと設定変更を拒否。他Hostも同じ記録で拒否（`focodex.py:637-669,764-773,797-809,838-842,879-882,946-966`）。読取専用のprojects等は可能。 |

`cleanup()` は対象PGIDへSIGTERMを送り、最大約1秒・20ms間隔で確認後、まだ存在すればSIGKILLを試みる。リーダーを最大3秒待ち、その後 `killpg(pgid, 0)` を1回行う。`ProcessLookupError` のときだけ消滅と判定し、`PermissionError` を含むOSエラーは未確認として例外扱い。`/proc` は存在判定後の診断用であり安全判定には使わない（`focodex.py:229-260,594-665`）。消滅確認とtoken照合後にのみ記録を削除する。

## 発見事項・重大度

1. **高: Host強制終了時にCodexが孤児として残りうる（コード上の欠落、実機未検証）。** `start_new_session=True` の子を親死亡に連動して終了する機構は見当たらず、SIGKILLではcleanupを実行できない。再現条件はCodex起動後にHostをSIGKILL、またはHostがfinally実行前に致命的に終了すること。子が自発的にEOF等で終了する場合もあるため、必ず残るとは言えない。記録が残る限り同一設定の再起動・競合操作は安全側に停止するが、不変条件4の孤児防止は成立しない。既存 `test_sigkill_leaves_durable_block_even_after_child_exits` は禁止維持を検証し、子を試験側で停止している（`tests/test_host.py:617-640`）。
2. **高: 別プロセスグループへ移った子孫を追跡できない（設計上の制約、実発生未確認）。** シグナルと存在確認は元のPGIDだけ（`focodex.py:606-633`）。子孫が `setsid` / `setpgid` 等で離脱して存続すると、元PGID消滅後に記録が削除され、同一設定の次の実行も可能になる。旧リポジトリへの書込みと次操作が競合しうる。不変条件1・3・4は全子孫に対して保証されない。離脱可能か、実際のCodexとそのサンドボックスで起きるかは別途検証が必要。
3. **中: 終了確認の単発判定で一時的な残存を永続的な未確認にしうる（コード上確認、個別原因は未確定）。** SIGKILL・リーダー回収後の確認が1回だけ（同:628-641）。その直後にグループが消えても同一bootでは記録が残る。Surfaceログの `193e26a5-7686-49b1-85df-c2a1f637e6d5` は判定時present、その後のスナップショットは全状態0・unreadable 1だが、読み取り不能対象の所属や消滅のタイミングは確定できない。安全性を保つ一方、可用性を損なう。
4. **中: リポジトリ変更後に旧応答が画面に残る（コード上確認）。** Aで応答を得た後Bを選ぶと、`project`/`workspace`変更はGit表示とモデルを更新するが `answer` と `info` を消さない（`probe.js:400-407,651-664,738-751`）。Bの新しい結果として内部的に取り込まれることを示す証拠はないが、表示には対象リポジトリが付かず、Bの結果と誤認しうる。不変条件2のUI上の明確性に問題がある。再接続時にも旧応答表示を消していない（同:516-537）。
5. **中: 排他は設定ファイル単位（仕様上の範囲）。** 異なる `FOCODEX_CONFIG` で同じリポジトリを扱うHost間や、Focodex外の手動操作とは排他しない（`focodex.py:25,263-264,724-735`; `specification/Git第2段階設計提案.md:26`）。同一設定での多重起動防止を全環境の保証と解釈できない。
6. **低〜中: 切断・異常終了の診断終端が欠けうる。** EOF時はfinallyでcleanupするがterminalを書かずreturnし（`focodex.py:1347-1349,1385-1387`）、SIGKILLでも当然記録できない。ログ上、進行中なのか切断済みなのか判別しにくい。安全判定には影響しない。

## 不変条件の判定

1. 多重起動: **条件付き成立**。同一設定・記録が保護され元PGID内に留まる範囲では、ロックと永続記録が起動を防ぐ。別設定・記録消失・離脱子孫は範囲外。
2. 旧結果の混入: **内部の通常経路では防止、表示は不十分**。busy中の切替禁止、接続・要求ID照合、実行ごとの状態初期化がある。一方、上記4の旧表示が残る。実機の競合試験は未実施。
3. 未確認時の競合禁止: **同一設定では成立**。ロック取得後の実行記録確認と、Host内未確認フラグによる拒否がある。ただし実際に離脱子孫が存在しても元グループ消滅を確認した場合は未確認として検出できない。
4. 孤児防止: **保証なし**。正常なEOF/SIGTERM経路はcleanupするが、Hostの強制終了と別PGIDの子孫には終了保証がない。

## 次回起動・復旧

同一boot IDの記録があればプロセスを探索・自動終了せず操作を拒否し、OS再起動でboot IDが変わった正常な記録だけを削除する。破損記録は自動解除しない（`focodex.py:224-227,267-301`）。これは存在確認ではなく保守的な復旧であり、Firefox/Hostの再起動では解除されない。再起動前に手動で記録を削除しない（`README.md:143-146`）。

## 推奨修正方針

1. まず安全境界を明文化し、Host死亡・グループ離脱を含む全子孫の終了保証が必要なら、OS管理の専用cgroup等、Hostとは独立した監督・終了確認機構を設計・実機検証する。PID再利用、権限、systemd利用可否、他のCodexへの誤殺と異常終了時の永続記録を含める。単純な親死亡シグナルだけでは全子孫や起動競合を保証できない。
2. 別途、合意済みの限定案としてSIGKILL後のPGID確認を最大1秒・50ms間隔で再試行し、`attempts` と単調時計の実経過 `waitedMs` を成功・失敗に記録する。`ProcessLookupError` のみ成功、PermissionError・期限切れは未確認、`/proc` は診断のみ。元PGID外の子孫対策にはならない。
3. プロジェクト・ワークスペース変更と再接続時に応答・実行情報を消す、または結果に実行対象とセッションを明示し旧結果と区別する。非同期応答は接続・IDに加え対象の整合性を検証する。
4. 同一設定単位という排他範囲を明示し、必要なら別設定での重複登録への対策を設計する。切断診断の終端と、Host強制終了で終端が残らない限界を文書化する。

## 修正後に必要なテスト

- 実機Firefoxでタブ閉鎖、再読込、通常終了、異常終了を、待機中・モデル取得中・Codex実行中・質問待ち中の各段階で行い、EOF/シグナル、プロセス、記録、別タブからの拒否・解除を確認する。
- HostのSIGTERM、SIGKILL、起動直前・起動直後・cleanup中・記録削除前後の異常終了。子・孫、グループ離脱、リーダー先行終了、ゾンビ、権限不足、PID/PGID再利用を隔離環境で検証し、他プロセスを誤終了しないことを確認する。
- killpgの即時消滅、数回後消滅、期限切れ、PermissionError、その他OSエラー、`waitedMs`/`attempts`、記録保持、別Hostの拒否を検証する。`/proc` 読取不能でも安全判定が変わらないこと。
- 同一設定の2画面と別設定の2 Hostで起動競合、Git・設定変更、旧応答遅延、再接続時の旧ポートイベント、リポジトリ変更後の表示と旧結果の混入を検証する。
- 同一bootでの禁止維持、boot ID変更による正常記録の解除、破損記録の保持、記録のtoken不一致・書込み/削除失敗を確認する。Git更新中の中断は結果不明として扱い、自動再送しない。

既存試験にはNative stdin切断時の子終了と2 Host排他、Host SIGTERM、SIGKILL後の記録保持、boot ID変更、停止時の終了確認がある（`tests/test_host.py:592-727`）。これらはFirefox実機の全終了経路や、離脱した子孫の保証を示すものではない。
