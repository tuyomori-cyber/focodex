# Focodex ワークスペース設計案

- 作成日：2026-10-21
- 状態：ワークスペースと検出・管理画面を実装済み。Firefox実機での管理操作と複数リポジトリ横断編集は未確認。
- 対象：複数リポジトリを横断する開発と権限の共有。

## 1. 推奨する構成

ワークスペースを「同じ開発権限で扱う、明示登録されたリポジトリの集合」とする。
物理的な親ディレクトリを用意したり、リポジトリを移動したりする必要はない。

| 概念 | 役割 |
| --- | --- |
| ワークスペース | Codexが読み書きできるリポジトリの集合、会話の所属先 |
| プロジェクト | 登録済みリポジトリ／作業ツリー。既存のproject IDを保持する |
| 開始プロジェクト | 指示実行時の作業ディレクトリ（cwd） |
| Git操作対象 | Gitパネルで明示選択する1リポジトリ |

例：`foxbook`ワークスペースに`focodex`、`fox-voice-editor`、`foxbook-control`を登録する。
開始プロジェクトを`focodex`にしても、同じ指示の中で他の2リポジトリを調査・修正できる。
開始プロジェクトの選択によって権限範囲は変化しない。

共通の親ディレクトリ全体に許可する方式は採用しない。登録していない隣接リポジトリや、後から作ったディレクトリまで許可されてしまうため。
1つのプロジェクトを複数ワークスペースに登録してもよいが、許可は選択中のワークスペースだけから計算する。所属関係をたどって他のワークスペースへ権限を広げない。

## 2. 権限

- 所属する全リポジトリの作業ファイルへ同じ読み書き権限を適用する。リポジトリをまたぐたびの承認は不要。
- 同じ権限には既存の制限も含む。各ルートのGit管理情報等の保護、外部通信禁止、汎用の権限昇格禁止を維持する。
- ワークスペース外の読み書きは従来と同様に禁止する。実行に必要な最小システムファイルとCodex実行ファイルの読み取り例外は維持する。
- 親ディレクトリ、未登録の兄弟リポジトリ、他ワークスペースには許可を与えない。
- Git変更操作は既存方針どおりNative Hostの専用機能で行う。ワークスペースへの登録によってCodexへGit管理情報の書き込み権限を与えない。

ワークスペースへの追加は、そのリポジトリに対する読み取り・編集・削除を許す設定変更になる。
初期版では端末内のHost設定を手動編集する。リポジトリ内の定義ファイルやCodexの出力から自動追加しない。
将来登録画面を設ける場合は、追加後の許可対象をユーザーに示して確定する。

## 3. 設定案と移行

既存の`projects`を再利用し、`workspaces`を追加する。`workspaces`のキーはHostが生成する内部IDであり、画面で表示・編集しない。
パスは端末ごとに保持し、ワークスペースとプロジェクトのIDは名前や絶対パスから分離する。

```json
{
  "codex": "/absolute/path/to/codex",
  "projects": {
    "focodex": {"name": "Focodex", "path": "/home/user/project/focodex"},
    "voice": {"name": "Fox Voice Editor", "path": "/home/user/project/fox-voice-editor"},
    "control": {"name": "Foxbook Control", "path": "/home/user/project/foxbook-control"}
  },
  "workspaces": {
    "foxbook": {
      "name": "Foxbook",
      "projectIds": ["focodex", "voice", "control"],
      "defaultProjectId": "focodex"
    }
  }
}
```

- `workspaces`がない旧設定は、プロジェクトごとに1件だけ所属する仮想ワークスペースとして解釈する。設定ファイルは自動上書きしない。
- `workspaces`を明記した場合は、その定義だけを利用する。定義が空・不正なら旧形式へフォールバックせずエラーにする。
- 未登録ID、空の所属一覧、重複ID、所属外の開始プロジェクトは拒否する。
- Hostで絶対パス、ディレクトリの存在と実体パスを確認する。存在しないメンバーを黙って除外して開始しない。
- 初期版では同一実体パスの重複登録とルート同士の包含を拒否し、境界を単純にする。入れ子リポジトリ／submoduleの別登録は後続課題とする。
- 実行開始時に設定と実体パスの一覧を固定する。実行中の設定変更は次の実行から適用する。
- シンボリックリンクの実体が実行ごとに変わった場合は、変更を表示して再確定するまで開始しない。実行中のリンク経由の逸脱もOS隔離で検証する。

## 4. 画面と会話

画面には「ワークスペース」「開始プロジェクト」と、許可対象のリポジトリ一覧を表示する。
Gitパネルには独立した「Git操作対象」を表示し、差分・ステージ・commit・pushの対象を常に特定できるようにする。
Git操作対象の切り替えはCodexの権限範囲や開始位置を変更しない。

- 実行中はワークスペース・開始プロジェクトの切り替えを禁止する。既存の同時実行1件とHost全体の排他を維持する。
- Codexにワークスペース名、全所属リポジトリの名前と実体パス、開始プロジェクト、共通の権限方針をHostから伝える。
- 他リポジトリの`AGENTS.md`が自動で読み込まれると仮定しない。対象リポジトリで作業する前にその指示を確認するよう伝え、実機で挙動を確認する。
- 会話・下書き・モデル選択はワークスペース単位で保持する案とする。開始プロジェクトと実行時の構成識別値も履歴に記録する。
- 別ワークスペースへ切り替える場合は別の会話として扱い、未送信下書きを保持する。
- メンバーの追加・削除・パス変更後に古いセッションの権限を流用しない。初期版は新規セッションで開始し、変更後の許可対象を表示する。将来の会話再開機能も構成の照合を前提にする。

現行Hostは毎回`ephemeral`なスレッドを作るため、会話保存の部分は履歴機能の実装時に適用する。
ワークスペース導入だけで会話継続が実現したとは扱わない。

## 5. Codexへの適用と検証課題

現行Hostでは`codex_args()`が単一ルート用のpermission profileを定義し、`thread/start.cwd`へ選択プロジェクトを渡している。
開始後はprofile ID、承認方針、`runtimeWorkspaceRoots == [cwd]`を確認している。
Git取得やモデル選択の要求も`projectId`を前提としている。

公式の[Permissions仕様](https://learn.chatgpt.com/docs/permissions)には、`permissions.<name>.workspace_roots`に複数のルートを登録し、それらへ共通の`:workspace_roots`ルールを適用する仕組みがある。
これは今回の要件に適している。CLI 0.163.0でAを開始位置、A・Bをprofile-defined rootとして実機検証した結果、A・Bへの読み書きが成功し、未登録Cとリンク経由のCへの読み取り・書き込みは拒否された。

実装案：

1. Hostがワークスペースの所属IDを検証し、正規化済みのパス一覧を解決する。
2. その一覧を起動時の一時permission profileの`workspace_roots`へ追加し、既存のファイル・通信制限を各ルートへ適用する。Codexの設定ファイルは変更しない。
3. `thread/start`には選択した開始プロジェクトの`cwd`とprofile IDを渡す。従来sandbox設定と併用しない。
4. 実効profileとルートを照合してからターンを開始する。

特に、**profileに定義したルートと`runtimeWorkspaceRoots`は別の概念**である。
CLI 0.163.0の`thread/start`応答では、`runtimeWorkspaceRoots`は開始位置Aだけであり、profileで追加したBは`sandbox.type="workspaceWrite"`の`writableRoots`に現れた。
実行時は`set(runtimeWorkspaceRoots) ∪ set(sandbox.writableRoots)`が、正規化した所属リポジトリ一覧と完全一致することを確認する。`sandbox.networkAccess=false`、`excludeTmpdirEnvVar=true`、`excludeSlashTmp=true`、profile ID、承認方針も従来どおり確認する。
この応答形式が変わる場合は、許可範囲を推測して開始せず、検証スクリプトを更新して再確認する。
同名profileの設定レイヤー合成で余分なルートが加わる場合も考慮する。
意図した範囲への限定を確認できない場合は開始せず、検証済みの単一ルート方式を維持する。

Native Messagingは`workspaceId`と`projectId`を受け取り、Host側で所属を照合する。ブラウザから任意パスは受け取らない。
`run`では`projectId`を開始位置、Git専用操作では操作対象として解釈する。
既存メッセージの互換処理も、旧設定の単一リポジトリという境界を広げないことを条件にする。
モデル一覧のキャッシュはワークスペース・開始プロジェクト・構成識別値を含め、以前の構成を流用しない。

## 6. Gitと横断開発の制約

ワークスペース全体の変更一覧は、リポジトリごとにグループ化する。
初期版の変更操作は1リポジトリずつとし、まとめてcommit・pushする操作は提供しない。
複数リポジトリにまたがる変更の原子的な確定や、自動ロールバックは保証しない。
Git変更操作とCodex実行はHost全体で排他し、同じリポジトリが別ワークスペースに所属していても競合させない。

worktreeの外部Git管理ディレクトリは、登録した作業ツリーとは分けて扱う。
Codexに外部管理ディレクトリの権限を追加せず、既存の専用Git Hostで実体を検証する。
共通資料や共有ビルド出力のための「リポジトリ以外の共有フォルダ」は初期版では登録対象外とし、必要時に別途設計する。

## 7. 導入順序と受け入れ条件

1. [x] 一時ディレクトリにA・B・未登録Cを用意し、実CLIで複数ルートと実効設定の照合を検証する。再実行は`python3 scripts/verify_workspace_permissions.py`。
2. [x] 設定解決と旧形式の互換、Hostメッセージ、画面の選択・許可対象表示を実装する。
3. Git対象選択を分離し、ワークスペース単位の変更一覧に対応する。
4. Firefox実機で横断編集、停止、設定変更後の再実行を確認する。

受け入れ条件：

- Aから開始した1ターンでA・Bを読み書きでき、Bを編集するための追加承認が不要。
- 未登録C、共通親ディレクトリ直下、別ワークスペース、外部リンク先は読み書きできない。外部の実ファイルが変化していないことも確認する。
- A・BのGit管理情報の保護、外部通信禁止、汎用承認不可が維持される。
- 不明な所属ID、欠落ディレクトリ、構成不一致、余分な実効ルートでターンを開始しない。
- 旧設定のままでは従来の1リポジトリだけが許可される。
- Gitパネルの操作は明示選択した1リポジトリだけへ作用する。
- 構成変更後に古い権限・モデル一覧・セッションを誤って流用しない。

この案は権限の単位をワークスペースへ広げる提案であり、複数セッションの並列実行やブラウザのウィンドウ管理は対象に含めない。

## 8. リポジトリ検出とワークスペース管理UIの次段階案

現在の実装では、プロジェクトとワークスペースを`config.json`へ手動登録する。
リポジトリをSSH等で端末へ配置した後の登録作業をFocodex内で完結させるため、次段階では専用の管理画面を設ける。

ここでは、次の三つを明確に分ける。

| 概念 | 内容 | Codexのファイル権限 |
| --- | --- | --- |
| 検出ルート | リポジトリを探すためにHostが走査する親ディレクトリ | 与えない |
| 登録プロジェクト | 検出結果からユーザーが選んだGit作業ツリー | ワークスペースへ所属させた場合だけ与える |
| ワークスペース | 同時に開発する登録プロジェクトの集合 | 所属プロジェクトだけに与える |

たとえば`/home/user/project`を検出ルートとして指定しても、その配下の全リポジトリへCodexがアクセスできるわけではない。検出結果から`focodex`と`fox-voice-editor`を選び、`foxbook`ワークスペースへ保存した時点で初めて、その二つだけがCodexの権限対象になる。

### 8.1 画面案

通常画面のワークスペース選択の横に「管理」を置き、次の順で操作する。

1. 検出ルートを選ぶ。初回は既存プロジェクトの親ディレクトリ候補を表示し、必要なら絶対パスを入力して追加する。
2. 「リポジトリを再検出」を押す。Hostが検出ルート直下と設定した深さだけを走査し、Git通常リポジトリとworktreeを一覧表示する。
3. 検出結果からリポジトリを選び、既存ワークスペースへ追加するか、新しいワークスペースを作る。
4. ワークスペースの開始プロジェクトを選ぶ。これはCodexの`cwd`であり、他の所属リポジトリの権限を増減させない。
5. 保存前に、追加後の「Codexが読み書きできるリポジトリ一覧」を確認して確定する。

通常の実行画面でも、ワークスペース・開始プロジェクト・許可対象一覧を常に表示する。実行中は管理画面を読み取り専用にし、実行終了後だけ変更を許可する。

「ルートプロジェクト」は画面上では「開始プロジェクト」と呼ぶ。リポジトリを含む親ディレクトリを指す検出ルートとの混同を避けるためである。

### 8.2 Host APIと設定案

Native Hostに任意コマンドや任意パスの読み取りAPIは追加しない。管理画面用に、次の固定操作だけを追加する。

| 操作 | Hostの処理 |
| --- | --- |
| `workspace_config` | 検出ルート、登録プロジェクト、ワークスペースの一覧を返す |
| `repository_scan` | 指定済み検出ルートだけを走査し、Gitリポジトリ候補を返す |
| `workspace_save` | 検証済みの検出結果だけをプロジェクト／ワークスペースへ保存する |
| `workspace_delete` | ワークスペースまたは未所属プロジェクトを設定から削除する。実フォルダは削除しない |

設定は次のように拡張する。`discoveryRoots`は走査対象であり、permission profileの`workspace_roots`へ渡してはならない。

```json
{
  "discoveryRoots": ["/home/user/project"],
  "projects": {
    "focodex": {"name": "Focodex", "path": "/home/user/project/focodex"}
  },
  "workspaces": {
    "foxbook": {"name": "Foxbook", "projectIds": ["focodex"], "defaultProjectId": "focodex"}
  }
}
```

保存は設定ファイルのロック、一時ファイル、`fsync`、原子的な置換を用いる。Hostが返した検出結果には実体パスとGit形態を含め、保存要求では検出時の識別子と実体パスを再照合する。ブラウザから渡された任意パスだけで登録・削除しない。

### 8.3 検出の境界

- 検出ルートは既存ディレクトリに限定し、`/`、ホームディレクトリそのもの、空文字、検出ルート外を指すシンボリックリンクは拒否する。
- 初期値は既存登録プロジェクトの親ディレクトリ候補とし、自動でホーム全体を走査しない。
- 走査は深さと件数に上限を設ける。隠しディレクトリ、`.git`内部、キャッシュ、依存物ディレクトリは走査しない。
- `.git`ディレクトリを持つ通常リポジトリと、`.git`ファイルを持つworktreeを候補にする。Git設定・フック・フィルターを実行して検出しない。
- 検出結果の採用時に、既存の実体パス重複・包含関係・ワークスペース内重複の検証を再利用する。
- SSH clone、手動配置、USB等でリポジトリを配置する経路はFocodexの対象外とする。Focodexは配置済みの作業ツリーを発見・登録する。

### 8.4 実装順序

1. [x] 設定の読み書きを原子的にする共通処理と、`discoveryRoots`の検証を実装する。
2. [x] Hostの限定的な検出・保存APIと、通常リポジトリ／worktreeの試験を実装する。リンク逸脱と上限超過の試験は追加する。
3. [x] Firefoxの管理画面を実装し、検出、追加、開始プロジェクト変更、削除の操作を追加する。実機確認はこれから。
4. 実機でリポジトリ配置後の検出、ワークスペース作成、横断編集、削除後の権限縮小を確認する。
