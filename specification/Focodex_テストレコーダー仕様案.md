# Focodex テストレコーダー仕様案

作成日: 2026-10-31  
状態: 検討用の仕様案。未決定事項は再検討し、実装前に確定する。実装・実機検証はまだ行っていない。

## 1. 目的と対象

SurfaceでFocodexのタッチ操作を行いながら、開発・保守用のSSH接続から観測を開始し、プロセスと操作診断の証跡を時刻付きで収集する。手動で3時点の一覧を取得・照合する負担を減らし、試験操作の実施と観測を分離する。

第1段階の機能は、①プロセス監視、②操作診断ログ収集、③テストケースの開始・終了マーカー、④ケースごとのレポート生成。仮称は `focodex-test-monitor`。Surface側で動作し、SSH経由で操作する案とする。

Focodex本体・拡張・Native Host・日常のタッチ操作環境の変更は対象外。監視ツールはプロセスにシグナルを送らず、診断元ログ、実行記録、設定を変更・削除しない。試験の自動操作、故障注入、子孫の終了保証、合否の自動確定は第1段階の対象外とする。

## 2. 利用の流れ（案）

1. Surface上でSSHから監視を起動し、新規の記録ディレクトリを用意する。
2. SSH入力などで `start D-05` と入力し、Surfaceをタッチ操作して試験する。
3. 試験区間の終わりに `end D-05` を記録する。必要なケースを繰り返す。
4. `quit` で収集を終了し、証跡とケース別レポートを確認する。SSH切断時にもそれまでの記録を保持し、後からレポートを再生成できる設計を検討する。

コマンド名・引数・入力方式は例であり未確定。試験前から稼働していたHostは、観測開始時に存在したプロセスとして記録し、生成時刻を推測しない。

## 3. プロセス観測

- Linux `/proc` の定期観測を候補とする。Native Hostを識別し、その子孫として観測したCodex CLI等についてPID、PPID、PGID、SID、状態、起動時刻を記録する。HostはPythonで動くため、実行ファイル名だけでなく起動引数等による識別が必要。無関係なCodexを名前だけでFocodex配下と判定しない。
- PID再利用を区別するため、PIDに加えて `/proc/<pid>/stat` の開始時刻とboot IDを識別に用いる案とする。カーネルの開始時刻の単位と壁時計変換、時刻ずれの表現は実装前に確認する。
- 生成・消滅のイベント時刻は、実際の瞬間ではなく「最初に観測した時刻」「存在しないと観測した時刻」とする。初回観測で既存のもの、監視中に初めて見えたもの、観測できなくなったものを区別する。
- 権限不足・一時的な読み取り失敗・走査失敗を記録し、読めないことだけで終了と判定しない。見えなくなった対象の確定条件は未決定。
- プロセスは親子関係・グループを変更できる。観測前に親子関係が切れた子孫、観測間に生まれて消えたプロセス、権限等で読めないプロセスは見逃しうる。元PGIDの消滅や観測対象の不在を、全子孫の終了証明として扱わない。
- 既定ではコマンドライン全体、環境変数、指示文・応答文を保存しない。識別に必要な情報だけ一時的に読み、結果として種別・関係・IDを記録する案。対象選択の信頼境界は未決定。

## 4. 操作診断ログ収集

- 既存の `operation-diagnostics.jsonl` を読み取り、監視開始後に追加された行を保存する案。既定パスはHostの環境に依存しうるため明示指定も可能にする。SSHとFirefoxの `XDG_STATE_HOME` が同じとは限らない。
- ログ未作成、読み取り不能、部分行、不正行、切断、ローテーション、ファイル置換・縮小、追跡漏れの可能性は成功として隠さず記録する。`.1` を含むローテーション追跡と重複防止、初回末尾の部分行の扱いは未決定。
- 元ログを変更せず、読み取った証跡を保持する。診断ログの追跡ID・時刻とプロセスを、時刻が近いだけで同一実行と断定しない。ケース区間をまたぐ操作や、秒単位のログ時刻と高精度な監視時刻の差を明示する。

## 5. マーカー・記録・レポート

- 手動のケース開始・終了マーカーを時刻付きで保存する。D-01〜D-07を利用例とし、名前形式、同時・入れ子ケース、開始漏れ・終了漏れ、重複時の動作は未決定。マーカーは実施者の入力時刻であり、厳密な操作時刻ではない。
- 各記録に壁時計時刻と、経過時間の比較に使う単調時計などを持たせる案。タイムゾーン、時計補正や再起動をまたぐ場合の表現は未決定。
- 1回の監視ごとに新規ディレクトリを作り、既存データを上書きしない。記録案は `events.jsonl`（プロセス・マーカー・警告）、収集した `operation-diagnostics.jsonl`、`report.md`。名前や形式は未決定。
- ディレクトリ `0700`・ファイル `0600` を基本とし、出力先の所有者・権限・シンボリックリンク・既存ファイルの扱いを安全に検証する。収集データにはPIDや診断情報が含まれるため、共有時の確認を促す。保存先・保存容量上限・保持期間は未決定。
- レポートはケースごとにマーカー、観測したプロセス変化、診断行と追跡ID、未確認・収集欠落の警告を時系列で示す。SSH切断や不完全な最終行があっても、保存済み証跡から再生成することを目指す。自動的に合格や全プロセス終了を確定しない。

## 6. 要検証・未決定事項

1. 観測周期（例の0.2秒は仮値）、負荷・短命プロセス捕捉率、Surfaceでの実用性。
2. Hostの識別方法と対象ユーザー・複数Host・複数設定・同名別プロセス・再親化／グループ離脱後の関連付け。識別不能な対象は不明として扱う。
3. `/proc` 読み取り失敗と実際の消滅の区別、PID再利用、ゾンビ、ネットワーク切断・監視再開時の記録。
4. 診断ログのローテーション・置換・短縮・部分行、読取開始位置と重複／取りこぼしの検出方法。
5. 対話式マーカー、SSH切断時の動作、後日レポート再生成のインターフェースと不完全記録の表示。
6. 記録先の指定、容量・保持期間、プライバシー、識別子・パスの保存範囲。
7. 停止・障害時の書込み保証、ディスク満杯・権限拒否・クラッシュ時の明示、二重起動時の扱い。

## 7. 実装後に必要な検証（案）

- 模擬 `/proc` と実プロセスで既存・生成・消滅、PID再利用、再親化、グループ離脱、ゾンビ、短命プロセス、読取不能と観測欠落を確認する。
- 診断ログの未作成、追記、部分行、ローテーション、置換、切詰め、権限不足を試し、欠落・重複の扱いと元ファイル不変を確認する。
- マーカー境界、ケース未終了、SSH EOF・異常切断、再生成、時計変更、出力先権限、既存ファイル、容量不足を確認する。
- SurfaceでSSH監視中にD-01・D-05等を操作し、端末側の手動観測・診断ログと比較する。監視なしとの動作差、負荷、記録の機微情報、観測限界を確認する。安全上の異常操作は隔離環境で行う。
