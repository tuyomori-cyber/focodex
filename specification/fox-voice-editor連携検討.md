# fox-voice-editor連携の実現性と初期検討記録

調査日：2026-10-22。コードとMozillaの公式API資料に基づく検討記録。以下の「現行コード」と「通信契約の案」は調査時点の初期案であり、現在の動作仕様ではない。

採用した現行契約は[受信バッファ連携API v1](draft-api-v1.md)に整理した。送受信、3件FIFO、受理済みID、明示反映、Undo・クリアと保存復元を実装済みである。Firefox実機通信試験は未実施。この文書のセキュリティ検討は、現行契約に矛盾しない範囲での背景資料として参照する。

## 結論

Firefox標準の拡張間メッセージングで実現できる。fox-voice-editorの「Focodexへ貼り付け」はプレビューと同じ文章を送り、Focodexは受信バッファへ保存する。ユーザーが「指示文へ」を押して初めて入力欄へ反映する。クリップボード操作、他拡張のDOM操作、新たなNative Host処理は不要。

現行仕様v0.1.3の第5節にある、送信元検証・受信バッファ・受信結果・自動実行禁止を具体化する。最初の反映先は指示文欄とし、追加質問の回答欄への反映は別段階で扱う。

## 調査時点のコードで確認したこと

| 対象 | 現状と変更点 |
| --- | --- |
| fox-voice-editor `extension/manifest.json` | 固定IDは`fox-voice-editor@foxbook.example`。送信先の初期値にはFocodexの固定IDを利用できる。 |
| `extension/model.mjs`の`joinedText()` | ブロックの文字列を区切りなしで連結。プレビュー・コピー・連携で同じ関数を使えば文字列が一致する。 |
| `extension/editor.mjs`、`editor.html` | コピーは実装済み。ボタン、送信処理、結果表示、送信先ID設定を追加する。 |
| Focodex `extension/manifest.json` | 固定IDは`focodex@foxbook.example`。受信保持を永続化する場合は`storage`権限を追加する。 |
| `extension/background.js` | 現在は操作タブを開くだけ。外部メッセージの受信・検証・保留管理と、操作ページとの内部通信を追加する。 |
| `extension/probe.js`、`probe.html` | 指示文は通常の`textarea#prompt`。実行中は無効化。受信反映と保留文のUIを追加し、反映後に`controls()`を呼ぶ。 |
| 指示文の初期値 | 接続試験用の文章が最初から入っている。残したままだと初回から置き換え操作が必要になる。連携導入時は初期値を空にし、試験文を入れる操作を別にする案を推奨。 |
| 両拡張 | 現在`onMessageExternal`などの拡張間通信処理はない。 |

## 初期案の経路（現行では採用しない）

1. fox-voice-editorでユーザーがボタンを押す。その時点の`joinedText(editorState)`を固定して送る。
2. `browser.runtime.sendMessage("focodex@foxbook.example", message)`でFocodexへ送る。
3. Focodexの背景スクリプトの`runtime.onMessageExternal`で受け、ブラウザ提供の`sender.id`が許可したIDと一致することを確認する。
4. 形式・長さ・未処理受信文の有無を検査し、受信文を1件だけ保持する。同時受信は直列化し、後続で上書きしない。
5. 操作ページは内部Portで背景スクリプトに登録し、受信文を取得する。別拡張のページを直接操作しない。複数タブへ同時反映せず、操作ページを1つに限定する。
6. 空欄かつ待機中なら指示文欄へ反映する。反映成功を操作ページから背景へ通知する。受信直後のページ起動・登録順に依存しない取得方式にする。
7. fox-voice-editorへ結果を返す。保留として受理した段階と入力欄への反映完了を区別して表示する。

現在のFocodexのツールバーボタンは既存タブも再読み込みするため、受信時にその処理を流用すると編集中の文や実行中の接続を失う恐れがある。受信用経路では既存タブを再読み込みしない。

## 初期案の入力欄状態別動作（現行では採用しない）

| 状態 | 提案する動作 |
| --- | --- |
| 空欄・待機中 | 受信文をそのまま反映。Codexへの送信はFocodexの実行ボタンで行う。 |
| 入力済み | 元の文章を保ち、受信文と「置き換え」「受信文を破棄」を表示。カーソル位置への挿入や追記は初期対象外。 |
| Codex実行中 | 受信文を保留し、実行中の指示文を変更しない。完了後も無条件には置き換えず、下書き保護に従う。 |
| 未処理の受信文あり | 新規受信を拒否し、送信側に再送が必要と表示する。 |
| Focodexの操作タブなし | 背景で受信文を保持してタブを開く。ページ準備後に取得する。保持だけなら「反映完了」と表示しない。 |
| 拡張が未導入・無効・旧版 | 接続失敗や不正な応答を表示し、元の文章は保持する。既存のコピー機能も使える。 |
| 操作タブが複数 | 反映先を推測せず拒否するか、単一タブ運用へ誘導する。 |

Split Viewでは、既に両方のページが表示されている場合に受信だけでタブを切り替えない案を推奨する。新しいタブを開く場合の配置とフォーカスは実機で確認する。同じFirefoxプロファイル内で両拡張を読み込むことが前提であり、別プロファイルや別端末への転送は対象外。

## 初期案の通信契約（現行では採用しない）

```json
{
  "type": "focodex.draft.receive",
  "version": 1,
  "requestId": "送信操作ごとのUUID",
  "target": "prompt",
  "text": "プレビューと同じ文章"
}
```

- 送信元は本文中の自己申告ではなく`sender.id`で判定する。
- `type`・`version`・`target`・`requestId`・文字列型を検査する。空白だけの文章と上限超過は拒否し、切り捨てない。空白・改行を勝手に整形しない。
- 長さは現行欄の`maxlength=20000`に合わせ、JavaScriptの`text.length`で20,000 UTF-16コード単位以内を両側で検査する。`.value`のプログラム代入は`maxlength`任せにできない。
- 応答に同じ`requestId`と、`applied`（反映済み）・`pending`（保持済み）・`rejected`（理由付き）を含める。非同期の反映結果を通知するなら送信元への追加通知か状態照会を設ける。
- 送信側は応答待ちの連打を抑止する。応答を失った場合は「結果不明」とし、自動再送しない。同じIDの再試行を識別して二重反映を防ぐ。
- `runtime.sendMessage()`は複数の拡張ページにも届き得るため、外部受信リスナーは背景に集約する。内部Portも接続元が自分の操作ページか検証する。

## 保持と権限

背景ページのメモリだけに受信文を置くと、その再起動で失われる。受理済みと通知する場合は、`browser.storage.local`への保存完了後に通知する案を推奨する。操作ページの下書きも、背景側の受信文を消す前に保存する。操作IDを使ってページ再読み込み後も反映を照合できるようにする。

拡張の再読み込み・Firefox再起動時も、自動実行や送信先プロジェクトの自動変更は行わない。保持データの削除時点は、反映済み下書きへの保存完了かユーザーの明示破棄とする。

送受信APIのために`management`、`scripting`、広範囲のサイト権限を追加する必要はない。`externally_connectable`の宣言に依存せず、受信ハンドラーのID検証を必須とする。送信先IDは既定値を用意し、現行仕様に従ってfox-voice-editor側の設定で変更可能にする。

## セキュリティ方針（2026-10-22追記）

状態別の反映・下書き保護の動作はユーザー了承済み。以下は受信口を作る際の安全策の検討。採用範囲と実装条件はAPI契約を参照。

### 推奨：固定の送信元検証と、下書き専用の受信口

1. 外部受信ハンドラーの最初に`sender.id === "fox-voice-editor@foxbook.example"`を厳密比較する。未指定・別IDは即時拒否し、本文の処理、保存、UI通知、タブ作成を行わない。本文の`senderId`や表示名で認証しない。許可元はコード上の固定値とし、外部要求から追加・変更できない。
2. 初期版の送信元はfox-voice-editorの`editor.html`に限定する。`sender.url`をURLとして解析し、`moz-extension:`、パス`/editor.html`、クエリ・フラグメントなしを検証し、欠落時も拒否する。これはID検証に追加する条件であり、URLだけで認証しない。内部UUIDは環境依存なので固定値を埋め込まない。送信側を背景経由に変更するときは許可する送信ページも再設計する。
3. 受け付ける操作はバージョン付きの下書き受信と、必要なら同じ送信元の要求IDに対応する結果照会だけにする。未知の操作や余分なキーは拒否する。受信オブジェクトをNative Hostへ転送したり、内部ハンドラーへ汎用ディスパッチしたりしない。
4. 外部からは実行、停止、Git操作、ファイルアクセス、Host接続、プロジェクト・モデル・権限の変更、既存下書き・会話・設定の読み出しを提供しない。応答は要求IDと最小限の受付状態・定型エラーに限り、既存文章やパスを含めない。
5. 本文はプレーンテキストとして`textarea.value`または`textContent`へ反映する。`innerHTML`、`eval`、URL遷移、コマンド文字列として利用しない。空文・型・長さ・要求IDの長さを検証してから保存し、メッセージ全体を設定や状態へマージしない。
6. 保留1件、重複IDの記録件数と有効期間の上限、許可元に対する頻度制限を設ける。拒否メッセージを本文付きで逐次保存せず、大量ログやタブ生成を防ぐ。ブラウザがメッセージを受信・複製する負荷自体をなくせる保証はない。
7. 内部Portも自分の拡張IDと`browser.runtime.getURL("probe.html")`に対応する送信ページを検証し、登録済み操作ページだけが反映完了・破棄を通知できるようにする。結果照会にも外部受信と同じ送信元検証を適用する。
8. 保存する受信文は端末内の`storage.local`に限定し、同期や本文ログを追加しない。受信経路をWebページ向けに公開する設定や、不要な外部Portリスナーを追加しない。

Firefoxが渡す`MessageSender.id`は送信メッセージの本文とは別のメタデータである。別IDで動く拡張が本文に許可IDを書いても通らない。一方、`sender.id`は許可した拡張のコードが無改変であることや、ボタンが人に押されたことまでは証明しない。

### Firefox固有の制約

MDNの互換性データでは`externally_connectable`はFirefox未対応である。Chrome向けの`ids`許可リストを追加しても、Firefox側の防御として数えない。別拡張からの配送自体を止めることと、受信後に拒否することを区別し、今回保証するのは後者とする。将来対応された場合も受信処理のID検証は維持する。

### 代替・追加策の評価

| 案 | 評価 |
| --- | --- |
| 固定ID検証＋送信ページ検証＋下書き専用 | 初期実装に推奨。別IDの拡張を拒否し、許可元からも強い操作へ進めない。 |
| 両拡張へ同じ秘密文字列を埋め込む | 採用しない。ソースから読めるため秘密として機能しない。 |
| 端末ごとに乱数トークンを生成し手動ペアリング | 追加防御の候補。ID検証と併用し、未ペアの同ID差し替えに対する壁を追加できるが、セットアップ・失効管理が必要。同IDの置換で保存領域を引き継いだり、端末や許可元が侵害されたりした場合まで防げる保証はない。自動交換だけでペアリングを完結させると、その時点の相手を信用することになる。 |
| Focodexで一定時間だけ「受信待ち」を有効にする | 常時受付を避ける追加策。毎回の操作が増えるため、現時点では任意案。 |
| 署名済み拡張を利用する | 常用時の配布・更新の真正性を支える。MozillaはAMOへの登録時にIDの一意性を確認する。一時読み込みの信頼性と同一視しない。 |

一時読み込みは開発者が任意のmanifestとコードを読み込める運用であり、Mozillaの説明にも同IDの一時拡張が既存拡張を置き換える挙動がある。したがってID検証は「信頼したfox-voice-editorがそのIDで動いている」という前提の境界であり、ローカルでの差し替えや許可元自身の侵害への完全な対策にはならない。常用時は信頼した読み込み元・更新を維持し、必要になれば署名済み配布を検討する。

初期案では固定ID検証を必須とし、ペアリングを必須にする必要性は低いと判断する。実行にはFocodex側の明示操作が引き続き必要であり、受信文に書かれた命令は実行操作として扱わない。

### セキュリティ確認項目

- 別ID・ID欠落・本文だけの許可ID指定で拒否し、保存・タブ生成・Host呼び出しがゼロであること。
- 許可IDでも送信ページ不一致、未知操作、余分なキー、過大な本文・要求IDを拒否すること。
- HTML・スクリプトに見える文章が文字として表示され、自動実行やURLアクセスにならないこと。
- 結果照会から既存文章・会話・プロジェクト設定を取得できないこと。
- 同時受信・連打・再送で保留上書きや多重タブ生成が起こらず、管理データとログが無制限に増えないこと。
- 模擬試験に加え、別IDの試験拡張から実Firefoxで送信して拒否を確認すること。同ID差し替えは別の信頼境界として扱うこと。

## 実装時の確認項目

- 模擬試験：ID偽装、形式不正、空文、長文、絵文字の境界、同時受信、重複ID、応答消失、下書き保護、保留中の拒否、自動実行がないこと。
- ページ連携：未接続でも受信可能、閉じた状態からの起動、準備中の受信、再読み込み後の復元、複数タブ、実行中と追加質問待ちの保留。
- Firefox実機：固定IDでの通信と応答、双方の手動再読み込み、Split Viewの配置・フォーカス、Surfaceのタッチだけで受信から明示実行まで進めること。

変更の中心は両拡張のJavaScriptとUI、Focodexの受信・下書き保存である。実現性の不確実さよりも、受信確認と下書き保護の整合が実装上の主な課題となる。

## 公式資料

- [runtime.sendMessage()](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/runtime/sendMessage)：別拡張のIDを指定する送信と応答。
- [runtime.onMessageExternal](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/runtime/onMessageExternal)：他拡張からの受信。
- [runtime.MessageSender](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/runtime/MessageSender)：ブラウザが渡す送信元ID。
- [externally_connectable](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/externally_connectable)：未指定時も拡張間通信は可能。Webページからの通信と区別する。
- [MDN互換性データ](https://github.com/mdn/browser-compat-data/blob/main/webextensions/manifest/externally_connectable.json)：Firefoxでは`externally_connectable`未対応。
- [Extensions and the add-on ID](https://www.extensionworkshop.com/documentation/develop/extensions-and-the-add-on-id/)：IDと署名・登録時の一意性確認。
- [Loading temporary add-ons](https://blog.mozilla.org/addons/2015/12/23/loading-temporary-add-ons/)：同IDの一時拡張による置き換え。
